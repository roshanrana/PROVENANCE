# FR-B-03 — the cross-tenant leak, and its mitigation, measured

**Date:** 2026-09-07 · **Repo SHA:** `a357e08` · **Run:** BARRIER cluster #15,
4m 44s, both matrix jobs green · 40 trials per profile, n=80 per verdict.
**This is the measurement BARRIER has owed since its requirements were written.**

## The result

| profile | cross-tenant probe | control | AUC | 95% CI | p | pre-registered verdict |
|---|---|---|---|---|---|---|
| **default** | **1.0000** | 0.0000 | **1.0000** | [1.0000, 1.0000] | 9.999e-05 | `attack_succeeds=True` |
| **hardened** | **0.0000** | 0.0000 | **0.5000** | [0.5000, 0.5000] | 1 | `at_chance=True` |

Both halves, on the identical schedule, judged by `common/stats/decision.py` —
the NFR-05 thresholds fixed before any attack code existed and untouched since.

**The attack works. The mitigation closes it. Neither claim stands without the
other and both are here.**

## What was measured

Per trial, with a fresh nonce so no trial can reach an earlier one:

1. tenant B sends `<nonce> <filler>`;
2. tenant A sends the **same text** — positive class;
3. tenant A sends a *different* fresh nonce nobody has sent — negative class.

Same tenant, same key, same length, back to back. The only difference is whether
another tenant had put that text in the router's prefix index.

The instrument reads `prefix_indexer_hit_ratio` around each single request:
`(sum_after − sum_before) / (count_after − count_before)`, refusing to record a
trial where the count moved by anything but one.

## The control that makes the hardened zero mean something

A zero can mean "partitioned" or "the index is broken". The same hardened job's
ground-truth step, run minutes earlier on the same cluster, says:

```
default   prefix index consulted 404 times, 402 matched a non-zero prefix, index size 8
hardened  prefix index consulted 404 times, 401 matched a non-zero prefix, index size 9
```

The index matches perfectly well under `hardened`. What goes to zero is
specifically **tenant A reaching tenant B's entry** — which is the claim.

## Read this honestly

**This is the strongest form of the attack, and it is a confirmation oracle, not
an extraction one.** Tenant A sends the victim's text *verbatim*, so the whole
prefix matches and the ratio is 1.0 by construction. What that establishes is
that an attacker who can **guess** a prefix can have the routing layer confirm
it — a real threat where the interesting prompts are predictable (a specific
counterparty name, a document, a template). It does **not** establish that
unknown content can be recovered, and nothing here should be quoted as if it
did.

**The intervals are degenerate, and that is arithmetic rather than precision.**
Every default probe is exactly 1.0 and every control exactly 0.0, so the
bootstrap has no variance to resample; [1.0000, 1.0000] means "no observation
disagreed", not "measured to four decimal places". Likewise `p=9.999e-05` is the
floor of a 10,000-permutation test — the smallest value it can report, not a
smaller one.

**Separation this clean is a property of this workload.** Identical prompts
match fully; disjoint prompts share no first block. A realistic workload with
partially-shared prefixes would land in between, and the ratio would become an
interesting continuous quantity rather than a binary one. That experiment has
not been run.

**One model server pair, one simulator, one prompt shape, 40 trials.**

## What it does not depend on

Nothing here is client-observable, and it does not need to be — ADR-011 already
established that a client sees nothing on the simulator and moved the
attacker-observable oracle to FR-B-09 on real vLLM. This is the operator-side
demonstration that rescope called for: measured from the router's own index,
which is the channel the mitigation actually closes.
