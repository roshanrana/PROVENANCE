# S-02, run #6 — a verdict that was wrong, and why it is kept

**Date:** 2026-09-07 · **Repo SHA:** `86dbc86` · **Where:** GitHub Actions,
`ubuntu-latest`, kind v0.33.0 · **Run:** BARRIER cluster #6, 4m 55s, green
**Verdict as printed: `ORACLE VIABLE`. That verdict is a false positive.**

This is the first time BARRIER's topology has stood up and the spike has run.
Both facts are worth recording. The verdict is not.

## What the run printed

```
probes: 24
  note: latency hit median=214.8ms miss median=214.5ms — NOT evidence either way
        on the simulator, which does not vary TTFT on cache hit vs miss (D-01).
        Recorded for completeness only.

client-observable discriminators: ['header:x-envoy-upstream-service-time']

VERDICT: ORACLE VIABLE — client-observable discriminator(s) found
```

## Why it is wrong

`x-envoy-upstream-service-time` is Envoy's own upstream latency for that
request, in milliseconds. Two requests essentially never take the same number of
milliseconds, so the header differs between **any** two probes regardless of
cache state. It classifies nothing.

The refutation is three lines above it in the same output. Hit median 214.8 ms
against miss median 214.5 ms — 0.3 ms apart — on a simulator that by
construction does not vary TTFT on cache hit versus miss (D-01, upstream issue
#347, closed as not-planned). The timing carried no cache signal, and the spike
counted a header derived from that timing as a signal anyway.

## The defect

`find_discriminators` implemented "fields that differ", while its own docstring
promised "fields that differ *for reasons related to routing*", and bridged the
gap with a five-entry ignore-list: `date`, `content-length`, `x-request-id`,
`server`, `connection`. An ignore-list only excludes the noise you already
thought of. `x-envoy-upstream-service-time` was not on it.

It is now a property test rather than a name list. A field counts only if it is

* **consistent** — differs in *every* hit/miss pair, not merely some; and
* **classifying** — its value is a property of the class, not of the request. A
  field taking a fresh value on every probe on both sides is measuring the
  request.

Fields that differ but fail either test are published in the evidence JSON under
`rejected_candidates`, with the reason. "We looked and rejected it" and "we never
looked" are different claims and only one of them is checkable.

**This is a defect fix, not a change to the decision rule.** LLD §7 fixes what
the *verdict* means and is untouched. It never said a differing field is a
signal.

## Why this run is kept

Because the project's claim is that its numbers can be checked, and the only way
to make that claim credible is to leave the checkable mistakes in. This is the
second time a result was published-shaped before it was right — see defect #6 in
the ship report, where a guard against a mislabelled comparison contained the
bug it was written to prevent, and produced an H100 result that was the exact
opposite of the truth.

The pattern in both: **the refuting evidence was already in the output.** A
32-trial cell finishing in zero seconds; a 0.3 ms median gap under a header
claimed as a discriminator. Nothing external was needed to catch either.

## What the run does establish

Independently of the verdict, run #6 is the first evidence that the topology
works end to end:

| | |
|---|---|
| EPP | 1/1 Running — `gRPC server listening name=ext-proc port=9002` |
| Gateway | 1/1 Running — `cm init: all clusters initialized` |
| Simulators | 2/2 Ready |
| Spike | 24 probes, gateway answered every one |

So F-18 (no `ext_proc` filter), F-20 (`ko` could not tag on a multi-node kind
cluster), F-21 (the EPP config named a plugin that does not exist) and F-22 (the
simulator's latency flags are Go durations) are all closed by a run rather than
by an argument.

## What happens next

Re-run under the corrected rule. **The verdict is not recorded in
`decisions.md` until then**, and no oracle code is written before it is — the
same discipline as S-03 and the pre-registered statistics. Both outcomes remain
publishable: `NO CLIENT-OBSERVABLE SIGNAL` rescopes FR-B-03 to an instrumented
demonstration, which NFR-17 was written to survive.

# Amendment — run #7 returned the same wrong verdict

**Date:** 2026-09-07 · **Repo SHA:** `677dee4` · **Run:** BARRIER cluster #7,
2m 9s, green. **Verdict as printed: `ORACLE VIABLE`, on the same header. Also
wrong.**

```
note: latency hit median=205.6ms miss median=216.0ms
client-observable discriminators: ['header:x-envoy-upstream-service-time']
VERDICT: ORACLE VIABLE
```

No rejection was printed at all, so the corrected rule did not merely disagree
about the header — it never fired.

## Why the first correction failed

It rejected a field whose values were **all distinct** on both sides. Millisecond
integers over eleven probes collide by chance — two hits both reading `205` is
unremarkable — so the all-distinct test was false and the header sailed through.

The correction was testing a *pattern in the values* when what disqualifies the
field is the **type** of the values. `x-envoy-upstream-service-time` is a
measurement. Asking "did it differ?" of a measurement is a category error, and no
amount of refining "differ" fixes a question that should not have been asked.

## The correction that actually addresses it

Continuous channels are separated from categorical ones and judged by the rule
this project already fixed in advance:

* **Categorical** — non-numeric fields. Must differ in every pair, and no value
  may appear on both sides, or seeing it tells a caller nothing.
* **Continuous** — latency and every numeric-valued header. Handed to
  `common.stats.decision.decide`: AUC with a stratified bootstrap interval and a
  permutation p, against the thresholds fixed in NFR-05 before any attack code
  existed. Each channel is scored in **both orientations**, keeping the stronger,
  because an attacker who notices that hits are the slower class simply inverts
  the test.

So the timing question is now answered rather than narrated. The previous output
printed two medians and a disclaimer; it now prints an AUC, an interval, a p, and
whether that clears the bar.

`--repeats` in CI moves from 10 to 30 — an interval over 22 samples was not worth
computing.

## The thing worth being uncomfortable about

This is the second correction to the same function in response to the same
unwanted verdict, and that is exactly the shape of tuning an analysis until it
says what you want. Three things distinguish it, and a reader is entitled to
check all three:

1. **The threshold moved nowhere.** NFR-05's AUC, p and confidence are untouched,
   and `tests/common/test_decision_thresholds.py` fails the build if they change.
2. **The rule is not about this header.** No ignore-list, no name. It is a
   statement about types of evidence, and it would have been written the same way
   before the run.
3. **The new path can still return ORACLE VIABLE.** If latency separates the
   classes on the simulator, the pre-registered rule says so and the verdict
   stands. The correction did not remove the channel; it made the channel
   answerable.

If run #8 returns `NO CLIENT-OBSERVABLE SIGNAL`, that is the rescope LLD §7
anticipated, and FR-B-03 moves to an instrumented demonstration with the
attacker-observable oracle deferred to FR-B-09 on real vLLM. That outcome was
publishable before any of this was written and it still is.

# Run #8 — `NO CLIENT-OBSERVABLE SIGNAL`, and why it is not yet recorded

**Date:** 2026-09-07 · **Repo SHA:** `ad6c680` · **Run:** BARRIER cluster #8,
2m 40s, green · 64 probes, n=62 per channel.

```
rejected: header:x-envoy-upstream-service-time — numeric-valued, so a measurement
          rather than a categorical label; judged by the pre-registered AUC rule
          under measurements, not here

measurements, by the pre-registered rule (NFR-05):
  header:x-envoy-upstream-service-time: AUC=0.5619 [0.4173, 0.7029] p=0.4075 n=62 clears_bar=False
  latency_ms:                           AUC=0.5567 [0.4100, 0.6993] p=0.4526 n=62 clears_bar=False

client-observable discriminators: NONE
significant measurements: NONE

VERDICT: NO CLIENT-OBSERVABLE SIGNAL — rescope FR-B-03 per LLD §7
```

Both continuous channels sit essentially at chance, with intervals straddling
0.5 and p around 0.4. The header that produced two false-positive verdicts is now
measured rather than counted, and measured it says nothing — which is what D-01
predicted all along.

**This is the outcome LLD §7 anticipated**, and it is a finding rather than a
failure: FR-B-03 rescopes to an operator-instrumented demonstration, and the
attacker-observable oracle moves to FR-B-09 on real vLLM.

## Why it is still not recorded in `decisions.md`

Because the spike prints its own caveat on every run, and it applies here:

> a spike that only looked client-side cannot tell "no signal" from "we did not
> look".

A negative result is only worth as much as the positive control behind it. If the
EPP's prefix index never recorded a match — because the profile declares
`prefix-cache-scorer` but the producer that feeds it never ran, say — then this
run measured a misconfiguration and would have published it as a security
property. That is the same error as F-14 and F-19: a check that passed because it
was run against the thing that accommodates it.

So the workflow now captures the EPP's own metrics and log after the probes, and
**fails the job** if the EPP reports no prefix-cache metric at all. The verdict
is recorded only from a run that carries that ground truth.

The correction to the analysis is separately load-bearing here. Under the rule
that stood before F-24, this same data would have printed `ORACLE VIABLE` — the
header still differs on every pair. The difference between "the attack works" and
"there is nothing to see" was, in this dataset, entirely a question of whether a
millisecond counter was treated as a label or as a measurement.

# Run #11 — the verdict earns its positive control, and the power question it exposes

**Date:** 2026-09-07 · **Repo SHA:** `22b27ee` · **Run:** BARRIER cluster #11,
2m 26s, green.

```
measurements, by the pre-registered rule (NFR-05):
  header:x-envoy-upstream-service-time: AUC=0.6296 [0.4885, 0.7664] p=0.07949 n=62 clears_bar=False
  latency_ms:                           AUC=0.6202 [0.4766, 0.7575] p=0.1061  n=62 clears_bar=False

client-observable discriminators: NONE
VERDICT: NO CLIENT-OBSERVABLE SIGNAL

ground truth: prefix index consulted 64 times, 62 matched a non-zero prefix,
              2 matched nothing; index size 8
```

## The control holds

`prefix_indexer_hit_ratio` recorded 64 observations for 64 probes, 62 of them
with a non-zero match, mean ratio 0.94 (`_sum` 60 over `_count` 64), index size
8. **The router had something to leak.** So this is a negative result about
observability, not an accident of a cluster where nothing was cached — which is
the distinction the last three findings existed to establish.

## Why it is still not the recorded verdict

Look at the point estimates rather than the pass/fail column:

| run | n | latency AUC | 95% CI | p |
|---|---|---|---|---|
| #8 | 62 | 0.5567 | [0.4100, 0.6993] | 0.4526 |
| #11 | 62 | 0.6202 | [0.4766, 0.7575] | 0.1061 |

Both sit **above** chance with an interval that straddles it. That is not
evidence of no effect; it is what n=62 looks like when it cannot resolve an
effect of this size. Publishing "no client-observable signal" from it would
overstate what the data supports, in the same direction the earlier runs
overstated it the other way.

The fix is power, not interpretation. `--repeats` moves to 200, so n=402 per
channel, **and that number is fixed in the workflow before the run rather than
after seeing it.** The verdict that run returns is the verdict recorded,
whichever way it falls. Re-running at n=62 until an interval happened to clear
chance would be optional stopping, and it is the failure mode this whole
sequence has been circling.

Worth stating plainly: at n=402 a real effect of AUC≈0.62 would likely clear the
pre-registered bar. So this is not a change that makes `NO SIGNAL` more likely —
it makes whichever answer is true more likely to be reached.

## A presentation defect fixed alongside

Run #11's gate printed *"prefix index consulted 128 times"* for 64 probes: the
histogram is published under both a deprecated `inference_extension_` name and a
current `llm_d_epp_` one, and the first version summed them. A count a reader
cannot reconcile with the probe count invites distrust of the gate itself. It
now reports one family and names it.
